## Abstract

A programmable logic controller (PLC) stops a machine and shows a fault code, but one code can have several causes. We asked whether a general language model, reading the event and I/O log of a simulated test rig, adds anything to a simple rule when recommending a lockout cause (T1), the next recovery step (T2), a maintenance level (T3) or the alarm to handle first (T4). The model (M1) was Qwen 3.5 4B with no additional training, answering with one letter; we read the probabilities of the choice letters at the first output token. The rule baseline (R0) maps the PLC's first fault code to candidate causes. We pre-registered four verdict rules and four predictions, fixed 26 input files by SHA-256 and ran one official set of 2,997 simulated runs (simulation; physical values assumed; no comparison with physical equipment). The pre-registration's hash was recorded before the run in a private repository only, and the decision to publish was made after the results (Section 7). The run departed from the pre-registered procedure in several places (Section 6): the replay check of the generated set, meant to come before the rules and the model, was run only after scoring (0 mismatches); the two-generation comparison passed only after one retry; the last change to the model's fixed inputs was not reviewed; and a cross-machine check was not done. **T1: both below the line.** The model's input had the fault codes removed, while R0 reads the first fault code. On the 165 cell-B lockouts whose first fault code left more than one candidate cause, R0 was right 90 times (0.545) and the rule-plus-model composite 40 times (0.242; difference −0.303, 95% interval −0.446 to −0.172): the rule was below 0.90 and the composite did not add 0.10. **T3: the rule is enough** — R0-T3 flagged 51 of 53 maintenance-needed runs with 0 false alarms in 108 runs; R0-T3 uses the same boundaries that defined the labels, so this shows agreement between rule and labels, not maintenance skill, and under the pre-registered tie rule the verdict could not depend on the model. **T2 and T4: consistency [PASS]** (R0 7,323/7,323 and 1,374/1,383; 0 dangerous wrong answers). Three of four predictions were correct (two of them, T2/T4 and T3, close to certain by construction); prediction 1 (R0 ≥ 0.95 on resolved lockouts) was wrong at 700/741 = 0.945. Changing only the order in which the choices were listed changed the model's top answer on 8,404 of its 10,387 test items (81%; 228 of the 10,387 had a single choice and could not change). The design was changed twice before the official run, after an AI cross-review found that the first version's T1 verdict was decided in advance. The result applies to one untrained 4B model and one prompting method, on simulated data.

## 1. Question

The PLC's ladder logic and safety functions stay as they are. On top of them, an advisory model that only reads the log of the seconds before or after a lockout makes a **recommendation**; it writes nothing to the PLC. The pre-registered question is: how often does that recommendation agree with the simulated rig's ground truth, which tasks a rule alone already settles under the Section 4 lines, and what changes when the model is added?

## 2. Why this is a simulation-only question

Faults, wear and operator actions are injected into a simulated rig whose PLC logic is run scan by scan, so every lockout has a known injected cause and every wear run has a known level. That ground truth does not exist on a physical line. The price is that all physical values in the rig are assumptions and no result was compared with physical equipment. This report says nothing about logs from a real plant (Section 7).

## 3. Experimental design

### 3.1 Rig, faults and labels

The rig has three cells: cell A, cell B (a belt conveyor with an inspection device, an arrival sensor and a pneumatic pusher with a rod brake that diverts boxes into a chute) and a packaging cell P. A generator injects single faults and combinations of two or three faults, plus slow wear, and records PLC events, inputs (%I), outputs (%Q) and HMI words for each run. The cause label of a lockout (`cause.root_class`) is decided by re-running the run with each injected fault removed in turn and by a fault-free baseline run. Removed before items are made: lockouts whose cause cannot be isolated to one fault; lockouts that still occur when any single injected fault is removed; lockouts that also occur in the fault-free baseline run; repeated lockouts with the same first code; inputs identical to one in an earlier split; and identical inputs with conflicting cause labels. Removed T1 windows in the official set [pre-registered count by kind]: repeated same code 133, fault-free baseline lockout 68, not isolable 109, still occurring with any single fault removed 28, same input as an earlier split 103, same input with conflicting labels 2 (T2: same input as an earlier split 187; T4: repeated same code 133, same input as an earlier split 104). The pre-registration also asked for these counts by split and category; that breakdown was not made (Section 7).

Cause categories in cell B (eight choices): supply-pressure loss, flow reduction, mechanical jam, brake, belt drive, sensor, inspection device, safety intervention. Cell A has two (sensor, safety intervention) and cell P two (safety intervention, packaging device). In this catalogue "safety intervention" means a safety function that worked as designed (emergency stop pressed, light curtain entered, packaging safety permit released); no fault of a safety device itself is injected.

Splits: train, val, test_seen and **test_unseen** (two- and three-fault combinations held out by combination key). The official set used a new master seed; the pilot set was used only to draft prompts and choices and was not reused. Official set: 60 injected runs per cell × split × cause category; wear runs: 26 repetitions per single wear channel in test_seen and 80 runs of held-out wear combinations (configuration keys `single_reps.test_seen`, `unseen_runs`); **2,997 runs, 20,016 windows, 127,453 files**. The generator also produced 75,405 record-noise variants (shifted, duplicated, missing or reordered lines); as pre-registered, they are counted only and were not scored.

### 3.2 Tasks

| Task | Input window | Ground truth | Question to the model |
| --- | --- | --- | --- |
| T1 lockout cause | 10 s before the lockout; **masked** (fault words D640, D641, D647, D648 and fault-code events removed) | Injected cause category | One letter among the cell's categories |
| T2 recovery step | 10 s after the lockout, with D641 (current recovery step shown on the HMI); fault words and fault-code events removed | Next step in the recovery table | One letter among steps 0–8 |
| T3 maintenance sign | 300 s, cut before the run's first PLC warning or lockout; only windows with no later warning or lockout, or with one at least 5 s later (`t3.lead_s`) | Injected wear level: normal, observe, maintenance needed (stroke time 1.08× / 1.15×; belt speed deviation 2% / 5%; chatter that passes the PLC input filter) | One letter among three levels |
| T4 alarm priority | Events within a 2 s group; masked | First event under a fixed priority table (safety > equipment protection > quality > production > information) | One letter among the group's events |

T2 and T4 are not model comparisons in this study: T2 re-reads a value the HMI already shows, and T4's answer is the priority table itself (Section 3.6). Only R0 consistency and dangerous wrong answers decide them. T1 is judged on cell B only, because in the pilot the cell alone fixed the cause in cells A (29/29) and P (48/48).

### 3.3 Methods

| Method | Definition |
| --- | --- |
| R0-full (T1) | Uses the **unmasked** first PLC fault code (D640). Code → candidate categories from a fixed expected-code table. One candidate: "rule resolved". Several: "rule unresolved", answer = the candidate most frequent in train |
| R0-masked (T1, reference) | Event-name → category mapping on the masked input |
| R0 (T2, T4) | Recovery table; priority table (falls back to R1 where the table gives no order) |
| R0-T3 | Stroke ratio ≥ 1.15, or belt deviation ≥ 5%, or chatter passing the filter → maintenance needed; ≥ 1.08 / ≥ 2% → observe. **These are the same boundaries that made the labels** |
| R1 | Most frequent train category |
| M1 | Qwen 3.5 4B (`Qwen/Qwen3.5-4B` commit `851bf6e8`, Apache-2.0), converted to BF16 GGUF with llama.cpp `7049ff0` (SHA-256 `7d9e8d79…c79ccc00`), no additional training, thinking mode off. Prompt order: log → question → choices → "answer with one letter". At the first output token, the probabilities of the choice letters among the top 100 tokens are renormalized. Each item is asked with min(5, n!) different orders of its n choices (fixed seed `e5-m1-perm-v1`; the first is the original order): of the 10,387 test items, 9,501 had five orders, 658 (two choices) had two and 228 (one choice) had one. The answer is the top category of the mean over orders. An item whose top category changes across orders is flagged for human review ("human check") and stays in the denominator |
| Composite C (T1) | R0's answer on rule-resolved items, M1's answer (masked input, choosing among all of the cell's categories) on rule-unresolved items; scores are never mixed within an item |

Instructions and choices were written in Korean. Logs longer than 120,000 tokens lost their oldest lines first, with no omission marker, and R0-T3 read the same truncated text as the model.

### 3.4 Measures

- T1 primary: top-1 accuracy on cell-B rule-unresolved items, test_seen + test_unseen together; test_unseen is also reported alone. Secondary: recall by category for four risk categories named by the domain review (Section 3.6) — safety intervention, brake, supply-pressure loss, mechanical jam; denominators below 20 are given as counts only. Confusion tables by split, the list of missed cases, test_seen items by number of injected faults.
- T3: recall and false-alarm rate per run. A positive unit is a run with at least one maintenance-needed window (a hit if any of its windows is flagged); a negative unit is a run with only negative windows. Flags on negative windows of mixed runs are counted as early alarms and not used.
- M1's T3 threshold is chosen on val as the highest value giving val recall ≥ 0.97.
- 95% intervals: bootstrap, 10,000 resamples (seed string `e5-score-boot-v1`, percentiles), clustered by combination key (T1, T2, T4) or by run (T3); Clopper–Pearson where a proportion is 0 or 1. Each measure draws its own resamples (the seed string is combined with the measure's name), so two measures with the same count can have slightly different intervals (for example C and M1 at 40/165). Ratios are compared as integers.
- Dangerous wrong answer: T4 = the true first event is safety-class and another is placed first; T2 = a step the recovery table cannot reach from the current step, or step 3 (finishing push, which the PLC rejects) when the answer is 4.

### 3.5 Runs, fixed inputs and invalidation

All runs were on one machine (NVIDIA GB10, aarch64, 20 cores, 121 GB unified memory, Ubuntu, NVIDIA driver 580.178.04, CUDA 13.0 as reported by `nvidia-smi` on 2026-10-08). The pre-registration fixes 26 inputs by SHA-256, including catalogues, schemas, the official set configuration, prompts, model record, rule code, scorer and verdict constants (`judge.json`); the scorer reads its lines only from `judge.json`. Rule tables were rebuilt from the official train split and their SHA-256 recorded before any test file was opened; the scorer refuses to score test items without that record. For this reason three released tables (`rules_r1.json`, `rules_t1_full.json`, `rules_t1_masked.json`) have SHA-256 values different from the pre-registration's Section 12 table, which lists the tables at freezing time: as Section 12-③ requires, they were rebuilt from the official train split and their hashes recorded before test was opened (rule-table record 2026-10-06T06:54:39Z, private commit `0e0e3f6`). `rules_t3.json` is unchanged.

A run is invalid if any fixed input hash differs, if the two generations of the set on the same machine differ, or if M1 fails (no choice letter in any order) on more than 5% of the judged items. At most two retries per cause. The pre-registered order (its Section 9) is: fixed-input check → two generations → independent re-run and ladder replay of the set → rules → model → scoring. Section 6 lists where the actual order differed.

412 windows (3 more were removed for a lead time under 5 s); 251 windows were truncated, and the rule and the model saw the same truncated text (0 mismatches). No stroke-time item reached "maintenance needed" before a PLC reaction (Section 7).

R0-T3 uses the label boundaries, so its 51/53 and 0/108 show that the rule and the labels agree; they are not evidence of maintenance skill.

[pre-registered] By channel, R0-T3 caught 37 of 38 belt runs and 20 of 21 chatter runs. In 19 belt-only runs the PLC never reacted to the deviation; these runs exist by design (v0.3 added belt-only runs with a 5–8% target deviation, and cell B has no belt-speed warning). R0-T3 flagged all 19; M1 also flagged all 19, which carries no information because M1 flagged every run. Of the 70 maintenance-needed windows, 4 had a later PLC warning or lockout, 21.2–28.6 s after the window ended; the other 66 had none. Early alarms on negative windows of mixed runs: R0-T3 0, M1 84.

**The T3 verdict did not depend on M1.** Under the pre-registered tie rule ("rule enough" wins when both "rule enough" and "model adds" hold), the verdict is "rule enough" as soon as R0-T3 meets its line, whatever M1's threshold. M1's threshold was in any case degenerate: it is chosen on val, which held only 2 maintenance-needed runs, so it came out at 0.065 and M1 flagged every run. The set-size change of v0.3 enlarged the test wear runs but left val at one repetition; this is a design defect. Together with the label boundaries in R0-T3, this means the T3 verdict carries no information about the model.

## 7. Threats to validity and what this report does not claim

- **The pre-registration was not recorded publicly before the run, and publication was decided after the results.** The pre-registration left publication open, to be decided after the results; the decision to publish was taken on 2026-10-08, after the verdicts were known. Results that are published only after being seen are open to publication bias. For our published reports TR-2026-02, -03, -04 (with its amendment 1), -06 and -07, the pre-registration hash was committed to the public repository (`PREREGISTRATIONS.md`) before the run; for E5 it was committed only to a private repository (commit `7650685`, 2026-10-06 13:53:45 KST). A reader can compare the released pre-registration with the hash given here but cannot verify, from a third-party record, that it was fixed before the results.
- It is a simulation. Faults, wear and the operator are simulated, all physical values are assumptions, and no result was compared with physical equipment.
- One model (4B, no additional training), one prompting method (first-letter probability), Korean instructions. Fine-tuned models and other methods were not tested; they are candidates a later version could examine. The result does not rank models.
- **R0-full sees the first PLC fault code; M1 does not.** This asymmetry is part of the design (the composite uses the code where it resolves the cause), so "model alone vs R0-full" is not a like-for-like comparison. R0-masked sees the same input as M1 but on the unresolved items it is no better than the majority baseline.
- **The composite as designed** let the model choose among all eight cell-B categories, not among the rule's candidates. Restricting it to the candidates (85/165, [exploratory], Section 5.1) would not have changed the verdict, but other ways of combining rule and model were not tested.
- **The T1 "rule enough" outcome was practically out of reach.** On unresolved items R0 picks the train-most-frequent of two or three candidates; reaching 0.90 would need one candidate to account for 90% of such items, and such a category would rarely leave the code unresolved. In practice the T1 verdict could only be "model adds" or "both below the line". This is a structural limit of the same kind as the v0.1 problem, found only after the results.
- **R0-T3 uses the label boundaries, and R0 for T2 and T4 is the table that defines the answer.** These checks show that rules and labels agree; they are not evidence that rules are good maintenance practice. With the tie rule, the T3 verdict carries no information about the model (Section 5.2).
- T3 val was too small: 2 maintenance-needed runs, threshold 0.065, M1 flagged every run.
- Stroke-time channel 0: the PLC reacts at a stroke ratio of 1.138 with a chute-arrival time-out (code 19) before the 1.15 boundary, so no stroke item reached "maintenance needed" before a PLC reaction. The belt-only maintenance-needed runs occur in test_seen only.
- 251 of 412 T3 windows were truncated to fit the 120,000-token limit; in the official test set the truncated T3 items kept between 126 and 203 s of the 300 s window (median 199 s), estimated as the share of log lines kept × 300 s, assuming lines are spread evenly in time. The rule read the same text.
- Cumulative counters in the log (for example the belt count input) reveal how long the run has been going. Truncated and full windows share one format, but elapsed time can still be computed. For an untrained model the risk is low; it is not measured.
- Cells A and P were not judged; there the cell alone fixes the cause, and the model's numbers there reflect a preference for "safety intervention" (Section 5.1).
- Catalogue gaps named by the AI domain reviewer of Section 3.6: no cylinder position-switch, valve or safety-device faults, no gradual supply-pressure or brake wear, no return-stroke trend, no I/O or power faults; "safety intervention" covers only safety functions that worked. Lockouts that also occur in the fault-free baseline run are removed from T1; this includes code-19 lockouts caused by the simulated operator not emptying the chute. Code-19 lockouts with an injected root cause remain (46 of the 165 unresolved items have first code 19). The packaging runner's reset and start wiring differs from its specification.
- Run-order deviations from the pre-registration (Section 6): rule tables built before generation 2 finished; the first determinism comparison failed on a header string and was resolved by one retry; judged items run first, with interim numbers computed before official scoring; the independent re-run and ladder replay done after scoring; the cross-machine check (E7) not done; the outputs carry commit `0e0e3f6` rather than the fixed commit (E7); the last code change committed without review.
- The pre-registration (its Section 3) asked for the removed windows to be counted by split and category; only counts by kind are reported (Section 3.1).
- Three released rule tables differ in SHA-256 from the pre-registration's Section 12 table because Section 12-③ required them to be rebuilt from the official train split (Section 3.5); a reader comparing only the Section 12 table will see a mismatch.
- The frozen v0.3 still carries a status row saying "draft, no official set generated" and a "next steps" list that predates the freeze. These are inconsistencies inside the frozen document, recorded here rather than edited.
- The pre-registration was not written for publication: it contains internal approval notes, private repository names and working paths. It is released unchanged because its hash is fixed.
- The 2,997 runs come from one generator and one catalogue; items within a combination key are not independent, so intervals are clustered by key or by run and no significance test is made.
- A regression test of the data tools (`phase5a_belt_default`) fails on this machine because one gzip header byte (operating system) differs; the decompressed content is equal.
- All reviews (pre-registration, cross-review, code reviews, the review of this report) were done by AI agents of the same family as the agents that wrote the code. No person reviewed the generator, rules, runner or scorer line by line.
