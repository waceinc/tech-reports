## TR-2026-01 in one paragraph

A command gate that pre-executes supervisory writes on a replica of the PLC program is a known approach. We asked whether adding a behavioral-equivalence check (confirming from observed transitions that the replica still matches the plant) reduces hazardous false passes. In a pre-registered five-arm comparison on a simulated PLC (three self-authored ladders, 869 labelled commands, thirteen official attempts, every one listed in the run ledger with its outcome), the arm with the check and the arm without it let through exactly the same hazardous commands issued while the replica was stale — 23 of 280 before a design revision and 19 of 278 after it, identical on every verdict count (p95 latency differs narrowly). The four person-exposure false passes that remain are writes made while a timer preset had been changed in the plant program only: a dormant program difference that produces no behaviour until the timer runs, so no observation-based check sees it. A static program-signature check has to come before any behavioral check; on protocols without a program signature (Modbus) the gate cannot see this class of change. Results are from a simulated PLC on one machine; no physical PLC comparison is included.

## TR-2026-02 in one paragraph

When a PLC scans faster than the plant model it is connected to (here 10 ms scans against a 50 ms plant tick), the connection must decide what input the PLC sees at each scan inside one tick. In a pre-registered comparison on one simulated cell (a shuttle conveyor, three self-authored ladders, 816 official runs, every combination run twice with identical trace hashes, 0 invalid), sampling inputs only at tick boundaries changed no test-bench verdict compared with restoring the in-tick input history (false alarm 0/1, missed negatives 0/2), and every applied output change came exactly one tick later at the input phases that occurred. It did miss short stop and emergency-stop pulses that restoration caught: a 15 ms pulse was missed in 7 of 10 phases under boundary sampling and in 0 of 10 under restoration. All four pre-registered predictions held. The result files, run records, ladders, the runner's input-restoration and verdict code and the analysis scripts are released in [TR-2026-02/](TR-2026-02/), so readers can recompute the test-bench verdicts and check the report's numbers against the released files without the private simulators; runs cannot be re-executed. Results are from a simulated PLC and a simulated plant model; no physical comparison is included.

## TR-2026-03 in one paragraph

A PLC ladder that passes a test scenario set can still lack an interlock the set never exercises. On three simulated cells with self-authored correct ladders, we removed one series interlock condition at a time (500 variants: all 25 of one cell and stratified samples of the other two, out of 1,316 target conditions) and ran each variant through a fixed scenario set (3,680 variant runs, 38 baseline runs, every baseline pair with identical trace hashes). 183 removals were revealed — 107 through a different hazard event in the plant model or a different number of defective parts at the good exit, and 76 through the test-bench verdict only (165 and 18 under the interpretation fixed before the results, which counts every event and every part's final outcome; the pre-registration's wording was made the main split after the results, in response to review). Of the 316 not revealed, 25 were never exercised by the scenarios, 244 were exercised but left the applied outputs unchanged, and 47 changed the outputs without changing the compared outcome or the verdict; one variant could not be classified because all its runs ended in a plant-model error. Both pre-registered predictions were wrong: the recovery and pack-handshake groups went unrevealed 11.68 percentage points more often than the safety group (predicted: at least 20), and 7.91 % of the unrevealed removals were unexercised (predicted: at least half). The bundle [TR-2026-03/](TR-2026-03/) holds the run records of all 3,718 runs (tick traces for one cell only; the other two cells' traces total 69.6 GB and are not released), the result files, the analysis code and scripts that rebuild all 500 variant ladders and recompute the checks that the released files allow. Results are from a simulated PLC and a simulated plant model; no physical comparison is included.

## TR-2026-04 in one paragraph

A PLC ladder that an LLM writes from a specification can pass a static check and a test that forces inputs and compares outputs, and still behave wrongly once it drives a plant. Before any run we registered the question: of the ladders that pass (1) a static check and (2) an input-forcing test, what share fails (3) a run connected to a simulated plant? Three generators (G1 Claude Code, G2 Codex CLI, G3 the local open-weight model Qwen3-Coder-Next Q6_K) worked on 21 tasks in three simulated cells, each inside an operating-system sandbox that blocked reads of the correct ladders and the plant model; 147 generation units were produced and 146 judged (G3 was stopped after its first repetition during the round, a deviation from the pre-registration). 109 ladders passed (1) and (2). The pre-registered rule that voids a blank-block output containing a comment string of the correct block was missing from the run code and was applied after the results; it voided 55 of the 109. **None of the remaining 54 ladders failed (3); without the rule, none of the 109.** As observed, the prediction (at least 10 %) was wrong under both counts. Two harness defects left some G3 units unjudged or short of a repair: under the bound rule the author chose after the results, the worst case is 5/59 (8.5 %), or 6/60 (10.0 %, at the line) under an assumption about one leak-flagged answer, so this run alone cannot show that the defects could not have changed the verdict; a post-hoc sensitivity analysis judged the 8 late G3 answers (none passed (1) and (2)). The zero holds only within what judge (3) looks at — six criteria, 1 to 6 scenario runs per cell and a plant model with assumed physical values — and the round contains no demonstrated case of a ladder that passes (1) and (2) and fails (3). The bundle [TR-2026-04/](TR-2026-04/) holds the pre-registration, the task specifications, the input-forcing tests, the fixed code, the generated ladders (public versions), the judging and generation records (tick traces for one cell only), the analysis and leak-check scripts with their outputs and the decisions about the study; the appendix listing the engine's supported instructions is released by SHA-256 only. Results are from a simulated PLC and a simulated plant model; no physical comparison is included.

## TR-2026-06 in one paragraph

A linear robot move taught as six joint values can be planned by numerical inverse kinematics that follows only the tool pose, so the tool can reach the target while the joints end elsewhere. In a pre-registered run on 12 robot-arm models of one simulator × 60 linear moves, the current planner ended on joint values other than the taught ones in 213 of 240 moves whose start and target wrist joint (J5) had opposite signs and in 38 of 480 other moves; a wrist-configuration label computed from the kinematics predicted the case-level outcome (223 of 232 against 3 of 447). A check constructed for the report, which keeps every other finding of the product checker but replaces the end-joint comparison by an end tool-pose comparison, would have let 73 of the 251 mismatches play back (29.1%); the pre-registered prediction of at least 30% was wrong. Using the taught target or a joint-space interpolation as the initial guess removed the end mismatch by construction, but only the same 25 of 240 crossing moves passed; the rest were blocked by the joint-speed finding, mostly after a single-sample jump of about 180° (model A).

## TR-2026-07 in one paragraph

A fleet of autonomous mobile robots (AMRs) that sends each vehicle back to its start position after it unloads drives empty on the way back; dispatching the vehicle from where it unloaded avoids part of that. In one simulated lab (18 x 12 m, six sites, obstacles, two chargers, five AMRs of three types, one fixed one-directional job list, 150 s of MuJoCo physics with assumed parameters) we pre-registered five predictions and two falsification conditions, built the lab 20 times from one layout file (each build gets new object identifiers, which changes the run) and ran each build under four dispatch rules. Empty travel per completed transfer under the rebalance rule divided by that under the return rule had a median of 0.867 (range 0.805 to 0.984) and was below 1 in all 20 builds; completed transfers were not fewer in 16 of 20 (fewer by 1 or 2 in 4); there was no vehicle-to-vehicle contact in 84 runs, and the low-battery vehicle docked in all 20 charge-variant runs. All five predictions held. The direction of the effect is largely fixed by where the start positions are, and the lab was tuned during development while watching the rebalance rule.

## TR-2026-08 in one paragraph

A PLC stops a machine and shows a fault code, but one code can have several causes. On a simulated test rig (three cells, faults and wear injected, physical values assumed) we asked whether a general language model reading the event and I/O log — Qwen 3.5 4B without additional training, answering with one letter, read from the first-token probabilities — adds anything to a rule that maps the PLC's first fault code to candidate causes. We pre-registered four verdict rules and four predictions and ran one official set of 2,997 simulated runs. On the 165 lockouts whose fault code left more than one candidate cause, the rule was right 90 times and the rule-plus-model composite 40 times (the model's input had the fault codes removed): both below the line. A maintenance rule flagged 51 of 53 maintenance-needed runs with no false alarm, but it uses the same boundaries that defined the labels, so this shows agreement between rule and labels, not maintenance skill. Recovery-step and alarm-priority checks passed for the rule. Changing only the order of the choices changed the model's top answer on 81% of its test items. The pre-registration's hash was recorded before the run in a private repository only, publication was decided after the results, and the run departed from the pre-registered procedure in several places; the report lists each departure.

## How these reports are published

- **Pre-registration.** The question, the metrics and the acceptance lines are fixed in writing before the official runs. The result is published whichever way it comes out.
- **Every run counts.** Each official attempt gets a number. Invalid and aborted attempts are listed in the report's run ledger with their cause.
- **Corrections.** A correction is published as a new version with its own DOI. [ERRATA.md](ERRATA.md) lists, for each error, what the earlier version said and what is correct. Earlier versions stay archived; the concept DOI always resolves to the latest.
- **What the numbers come from.** Each report names the result files and commits its numbers were computed from, and states whether those files are public.
- **What is not published.** Customer data, customer names or identifiers, and customer drawings. Results that belong to a funding agency under a grant agreement are not published here without that agency's consent.
- **AI tools.** Reports state how generative AI was used in the work. The named author is responsible for the content.
